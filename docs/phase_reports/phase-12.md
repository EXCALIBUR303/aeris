**PHASE:** 12 — Classical planning + exploration baselines.

**IMPLEMENTED:**
- `aeris.autonomy.planning.astar`: 8-connected A* over a `BandGrid`, octile heuristic, configurable `unknown_cost_multiplier` (default 1.0 — unknown cells cost the same as free, needed for frontier exploration to path through unmapped space). `OCCUPIED` cells are never traversable.
- `aeris.autonomy.exploration.base`: `Subgoal`, `AgentPose`, the `ExplorationStrategy` protocol (`select_subgoal(grid, pose, t_s) -> Subgoal | None`) — the exact shared interface spec asks Phase 12 to build for Phase 19's future learned policy to also implement. The ADR-0015 egocentric candidate geometry (12 bearings x 2 ranges) and cell-snapping helpers, shared by all three strategies.
- `aeris.autonomy.exploration.random`: `RandomExploration` — uniformly samples a reachable egocentric candidate plus an equally-likely rotate-in-place option (H0.1's lower bound).
- `aeris.autonomy.exploration.frontier`: `NearestFrontierExploration` (Yamauchi 1997) — nearest reachable frontier cluster by A* path length, not raw geometric distance.
- `aeris.autonomy.exploration.utility`: `UtilityFrontierExploration` — score = (unknown-cell gain, estimated by raycasting the agent's own map) / (A* path length + `lambda_turn` x turn cost).
- `aeris.evaluation.metrics.coverage`: `coverage()`/`running_coverage_trace()`/`reachable_free_cells_gt()` — the evaluator's GT-pose-raycast coverage metric (spec §41), independent of either method's own map.

**SIMULATION RESULTS (the H0.1 exploration experiment, spec §51 Phase 12):**

3 val-split worlds (one per procedural family, seed 10000 each) x 3 methods x 3 repeats = 27/27 live episodes completed, 0 launch failures. Mean `C(180s)` per world/method (full per-episode data in `results/experiments/p12_exploration/{runs.jsonl,summary.md}`):

| World | random | nearest_frontier | utility_frontier |
|---|---|---|---|
| f1_rubble_10000 (dense, many small obstacles) | **0.372** | 0.157 | 0.150 |
| f2_office_10000 (small, enclosed rooms) | 0.899 | 0.900 | **0.959** |
| f3_warehouse_10000 (large, open aisles) | 0.206 | 0.204 | **0.212** |

**H0.1 decision:** pooled paired bootstrap CI (nearest_frontier - random, n=9 paired episodes): point estimate **-0.072**, 95% CI **[-0.164, +0.009]** (includes 0). H0.1 is **not rejected** -- frontier does not beat random by the pre-registered margin; the point estimate in fact trends the other way. See PROBLEMS FOUND #7 and docs/exploration.md for the full diagnosis: the effect is driven almost entirely by `f1_rubble_10000` and traces to the collision shield intervening far more (85-87% of ticks vs random's 81%) when a strategy specifically targets the boundary of the known map, which in a densely cluttered field is disproportionately adjacent to yet-unmapped obstacles -- `f3_warehouse_10000`, where all three methods draw similarly near-universal shield intervention (93-98%) regardless of targeting strategy, shows correspondingly no difference between them, consistent with this mechanism rather than a strategy-specific defect.

**Planner latency:** measured via a standalone CPU-bound benchmark (`select_subgoal()` + `astar()`, timed directly on a synthetic-but-realistically-scaled grid -- 81x81 cells at 0.2m resolution, matching the experiment's own window/resolution; honestly labeled synthetic, since no live episode's grid was saved to disk during the main run). p95 = 5.5ms (random) / 6.8ms (nearest_frontier) / 7.5ms (utility_frontier); bare `astar()` call p95 = 0.48ms. All comfortably under the 100ms gate.

**PROBLEMS FOUND:**
1. **A live wiring smoke test flew for 75 real seconds and made zero subgoal choices** (only 6 in-place rotation attempts). Root cause: all internal replan/rotation-timing decisions (`max_replan_interval_s`, the rotate-scan's own duration) were gated on a synthetic counter incremented by a fixed 0.1s per loop iteration, while the outer loop's own exit condition used real `WallClock` time. Phase 11 had already measured this same control-loop shape's real per-iteration cost at ~500-700ms (a synchronous GT-pose subprocess poll dominates); over 75 real seconds, the synthetic counter reached only a small fraction of its intended value, badly distorting every duration-based decision. This is new, Phase-12-specific exposure of an existing imprecision (Phase 10/11's own `elapsed`/`clock.now()` pattern has the identical drift, but neither of those modules has any *inner* duration-gated decision sensitive to it).
2. **Fixing #1 alone did not fix the stall** — still zero subgoals chosen across 31 independent re-evaluations at different yaw angles after the fix. Root-caused via a standalone diagnostic script (not guesswork): `project_band()`'s literal spec §21.1 rule ("free if *all* voxels in the band are observed free") combined with a forward-looking, ~58°-vertical-FOV depth camera flying *level* at a single hover altitude structurally never satisfies that requirement — direct inspection of a `VoxelMap`'s raw per-voxel state at a column 1m away showed the lower half of the altitude band genuinely observed free (5 real `False` states) but the upper half *never touched at all* (4 `None` states) even after many yaw rotations over 40 real seconds. Frontier detection requires a FREE cell to exist at all, so with none ever appearing, no frontier — and no subgoal — could ever be found. Phase 11's own report had already documented the identical free-classification limitation for its own hover-and-yaw sweep and named "multi-waypoint coverage" as Phase 12's job to solve; Phase 12, in trying to deliver that movement, discovered the strict free-rule itself was what was preventing any movement from starting.
3. **`NearestFrontierExploration`/`UtilityFrontierExploration` defaulted to `min_cluster_size=2`**, excluding lone-cell frontiers as presumed noise with no strong justification — live-tested and found this also starved early exploration, since the only frontiers that exist right after takeoff are frequently single cells at the observed area's own ragged edge.
4. **A design gap caught by unit testing, before any live flight**: the agent's own current cell can itself be a valid frontier (it borders unknown space -- the literal condition of standing at the edge of what's known), and for a cluster shaped symmetrically around the agent, the whole cluster's centroid can coincide with the agent's own cell -- an early fix (exclude the agent's cell from consideration, then re-check whether the *cluster* is now empty) would have discarded that cluster's other, perfectly real cells too.
5. **`_ensure_world()`'s first draft mis-used `generate_batch`'s own `n` parameter** (passing `seed + 1` under the mistaken assumption `n` selects a specific seed, when it actually means "generate the first n seeds of the split's own range") -- caught by a pure dry-run of the world-generation/config-loading logic before any live sim time was spent on it.
6. **The main experiment's first live episode stalled for minutes in pure CPU computation after the flight itself had already landed and disarmed.** Timed directly: `reachable_free_cells_gt()`'s call to `voxelize()` at the agent's own `mapping.resolution_m=0.2` over one val world's full 24m x 24m x 6m bounds (74 box primitives) took **14.83s**; the identical world at `0.5m` (Phase 9's own established convention for reachability-style whole-world computations) took **0.95s** -- a 15.6x difference matching the voxel-count ratio (432,000 vs 27,648) exactly.
7. **`random` scored dramatically higher coverage than both frontier methods on `f1_rubble_10000`** (0.37 vs 0.15-0.16) -- the opposite of H0.1's expected direction, triggering spec's own "this is a baseline bug signal: diagnose before proceeding" instruction. See SIMULATION RESULTS and VALIDATION GATE below for the full diagnosis and its conclusion (a real shield-throttling interaction with frontier-seeking's own targeting behavior in densely cluttered environments, not a code defect).

**PROBLEMS FIXED:**
1. Replaced the synthetic per-tick counter with `state.t_sim_s` (PX4's own reported sim clock) for every internal replan/rotation-timing decision -- accurate regardless of how long any given tick's real work takes. Confirmed live: rotation-attempt count in the same ~75s window went from 6 to 31, a cadence consistent with the intended 2-10 second decision intervals.
2. Added a `free_rule: Literal["all_observed", "any_observed"]` parameter to `project_band()` (`aeris/mapping/projection.py`), defaulting unconditionally to the existing `"all_observed"` behavior (zero change for every existing caller, including Phase 11's own already-validated map-accuracy evaluation). `run_exploration_episode()`'s own `project_band()` calls pass `"any_observed"` (free if at least one voxel in the band was observed and none of the observed ones are occupied) -- confirmed live: the same smoke test passed on the first attempt after this fix, using the identical unmodified 1.7m-tall altitude band, with real subgoal choices from the first tick onward.
3. Changed both strategies' `min_cluster_size` default from 2 to 1, matching Yamauchi's own definition (a lone free cell bordering unknown is a genuine frontier, not noise).
4. Both `NearestFrontierExploration.select_subgoal()` and `UtilityFrontierExploration.select_subgoal()` exclude the agent's own current cell from a cluster's candidate-cell set *before* picking the cell nearest that cluster's centroid, not after -- so a cluster that merely touches the agent's position keeps its other real cells available.
5. Fixed to call `generate_batch(..., n=1, ...)` -- correct because this experiment only ever wants each split's very first seed (`seed_per_family` is defined to equal `SEED_RANGES[split].start`), with an explicit guard raising if that invariant is ever violated.
6. Added a separate `coverage_resolution_m` config value (0.5), used only for the evaluator's own GT-coverage computation, independent of the agent's own live mapping resolution -- coverage is a "did you see this general area" question, not an obstacle-detection question, so the coarser resolution doesn't compromise what's measured. Both `reachable_free_cells_gt` and `running_coverage_trace` calls use the same value, since their cell indices must match for the intersection to mean anything.
7. Not "fixed" in the sense of a code change (it isn't a bug) -- diagnosed and reported as this phase's own real research finding (spec's own "No fake success" principle: "any outcome, including H0 not rejected, is reported plainly"). One genuine improvement was made and kept regardless of its effect on this specific result: `max_replan_interval_s` raised from 10.0s to 45.0s (see PROBLEMS FOUND #1's own timing fix; the default was too aggressive as a routine interrupt once arrival/map-change triggers already handle genuine progress) -- a standalone re-check of `f1_rubble_10000`/`nearest_frontier` after that change still scored 0.150, confirming the shield-throttling mechanism, not replan cadence, is the dominant effect.

**KNOWN LIMITATIONS:**
- The H0.1 experiment ran **3 val-split worlds, one per procedural family, 3 repeats each** -- a much smaller grid than an ideal "many worlds per family" design, for the same honestly-documented live-sim time-budget reason every prior phase's experiment scoped down (Phase 9: 8/family not 50; Phase 10: 5 runs not 10; Phase 11: 5 worlds not spec's own larger implied set).
- `lambda_turn` tuning used n=1 episode per candidate value on a single world -- the resulting spread (0.120-0.127 coverage) is well within plausible SITL run-to-run nondeterminism at this budget (spec §40's own D1 characterization), so the "winning" value (0.0) is reported as the grid's nominal best, not a statistically distinguishable finding.
- Utility-frontier's information-gain estimate raycasts a full circle from each candidate rather than the sensor's actual FOV, since the strategy doesn't commit to a particular arrival heading -- a deliberate simplification, documented in the module's own docstring.
- No 3D/multi-altitude exploration -- spec's own V1 scoping keeps exploration within a fixed 2D altitude band; the free-classification fix (PROBLEMS FIXED #2) works within that scope, not around it.
- `PathFollower` is still driven waypoint-by-waypoint by the episode runner tracking a path index, not a genuine carrot/pure-pursuit polyline follower with speed/curvature limits along the path (spec §24's fuller description of that component) -- out of this phase's scope to build; the existing single-goal `PathFollower.compute_velocity()` (Phase 10, unmodified) is reused as-is against successive waypoints.
- `lambda_turn` tuning used `coverage_resolution_m` at the time still equal to `mapping.resolution_m` (0.2, before PROBLEMS FIXED #6's voxelization-performance fix); the main comparison run used the coarser `coverage_resolution_m=0.5` throughout. This does not affect the tuning *decision* (a purely relative comparison among lambda values at one consistent resolution) but means the tuning run's own absolute coverage numbers (0.120-0.127) aren't directly comparable to the main run's.

**REMAINING RISKS:**
- The shield-throttling diagnosis for H0.1's result (PROBLEMS FOUND #7, docs/exploration.md) is a coherent, well-evidenced explanation -- the world-dependent pattern (severe in dense rubble, negligible in warehouse where all methods draw equally heavy throttling, moot in the small office world where everything converges to near-complete coverage) is real, measured data, not speculation -- but it has not been confirmed by a *controlled* ablation (e.g., re-running with a looser `inflation_m` or shield margin to see if frontier's disadvantage shrinks). That ablation is a natural next step but is out of this phase's scope.
- Utility-frontier's `lambda_turn=0.0` carries real uncertainty (tuned at n=1 episode/value, a spread within plausible SITL noise) -- a future phase relying on this specific value for anything beyond a baseline comparison should re-tune with a larger budget.
- `run_exploration_episode()`'s map uses the new, more permissive `free_rule="any_observed"` -- any future phase reusing this module's map for a purpose closer to map-accuracy evaluation (rather than exploration/planning) should use the stricter default explicitly, not assume this module's own choice applies.

**VALIDATION GATE (spec §51 Phase 12):** *"H0.1 evaluated with a pre-registered rule (frontier > random by ≥ 10 pp C(180 s) on val worlds, CI excluding 0). If it fails, this is a baseline bug signal: diagnose before proceeding. Planner latency p95 < 100 ms."*

| Requirement | Result |
|---|---|
| H0.1: frontier > random by >= 10pp C(180s) on val worlds, CI excluding 0 | **FAIL** -- point estimate -7.2pp (frontier trends *worse*), CI [-16.4pp, +0.9pp] includes 0. Diagnosed per spec's own instruction, not just reported: traced to the collision shield intervening more when a strategy specifically targets the boundary of the known map in a densely cluttered world (`f1_rubble_10000`), confirmed via shield-intervention-rate data and a consistent world-dependent pattern (absent in `f3_warehouse_10000`, where every method draws equally heavy intervention). No implementation bug found in extensive unit + live diagnosis. |
| Planner latency p95 < 100ms | **PASS** -- 5.5-7.5ms across all three strategies (synthetic CPU benchmark, honestly labeled as such). |

**VALIDATION GATE: FAIL** -- this phase's primary, decision-driving validation item did not clear its pre-registered bar. Per spec §6's own "No fake success" principle ("any outcome, including H0 not rejected, is reported plainly"), this is reported as a straightforward fail, not reframed as a partial pass: H0.1 is a sanity check, and the honest result is that classical frontier exploration, as implemented and shielded here, does not demonstrate a coverage advantage over random search at this phase's scope -- if anything the reverse, in the one world where obstacle density is high enough for it to matter. The implementation itself is not in question (thoroughly unit-tested, no bugs found in extensive diagnosis, and planner latency clears its own gate with a wide margin) -- what failed is the hypothesis this specific classical baseline set out to confirm.

**CURRENT AERIS STATUS:** AERIS now has real classical global planning (A*) and three exploration baselines (random / nearest-frontier / utility-frontier) wired into a live, safety-shielded control loop -- closing the "no planning or exploration exists yet" gap every earlier phase's docs flagged, and building the exact `ExplorationStrategy` interface Phase 19's learned policy will later also implement. The H0.1 result is a genuine, load-bearing research finding rather than a "sanity check passed, move on" formality: naive frontier-seeking's vulnerability to collision-shield throttling in densely cluttered environments is real, measured, and world-dependent, and any future phase tuning `inflation_m`/shield margins, designing utility-frontier's own scoring more carefully, or building the learned exploration policy this baseline set is meant to be compared against needs to account for it rather than assume frontier-following is a safe, unexamined default.
